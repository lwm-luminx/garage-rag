# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this is

Garage is a local-first personal RAG (Retrieval-Augmented Generation) pipeline over PostgreSQL +
pgvector. It indexes personal documents, code repos, and communications with automated authorship
attribution, multi-model vector embeddings, hybrid full-text/vector search (Reciprocal Rank
Fusion), and serves the corpus over MCP 2.0. Three deployable pieces:

- **`rust/`** — the Cargo workspace: the backend (`garage-service`, the gRPC `GarageService` over
  Postgres + pgvector), the ingest pipeline and its readers (`garage-ingest`, `garage-readers`,
  `garage-text`, `garage-ocr`, `garage-git`), the embed worker (`garage-embed`), the MCP server
  (`garage-mcp`) and the command line (`garage-cli`: the `garage` CLI and the `garage-mcp` stdio
  server). The `*-ffi` crates export each piece over a C ABI for the apps.
- **`macapp/`** — `GarageApp`, a native Swift/SwiftUI macOS menu-bar app that bundles a relocatable
  Postgres 18 + pgvector instance and runs the Rust pieces inside its XPC services.
- **`proto/garage.proto`** — the gRPC contract between the apps and `GarageService`: corpus
  access (search, documents, sources, models, stats), every operation the app runs (sources,
  models, scan, sync, backfill, enrich-facts, settings, MCP client registration), and the database
  facade the ingest and embed workers persist through. The app never shells out to `garage`.

The Windows app (`winapp/`) runs the same Rust libraries behind a WinUI 3 shell. The Python package
the pipeline started as is gone ([docs/plans/python-removal.md](docs/plans/python-removal.md)); the
`.py` files left in the tree are development tools, and each Rust crate's docs name the Python module
it ports, for reading the history.

## Build system

This is a Bazel monorepo built via **Aspect CLI** (wraps Bazel; use `aspect` in place of `bazel`).
The Rust code is also a plain Cargo workspace (`rust/`), which is the fast loop; Bazel builds the
same crates through rules_rs for the app. The `BUILD.bazel` files under `proto/` are generated by
`aspect gazelle` and should be regenerated rather than hand-edited.

```bash
# One-time environment setup (direnv-based; puts aspect/format/etc. on PATH)
direnv allow
bazel run //tools:bazel_env

# Build everything / just the macOS app
aspect build //...
aspect build //:macapp

# Test everything
aspect test //...

# Format (Ruff for the Python development tools, buildifier for Starlark) and lint (Ruff)
aspect format -- //...
aspect buildifier
aspect lint //...

# Regenerate BUILD files after editing proto/
aspect gazelle

# Generate an Xcode project for the macOS app
aspect run //:xcodeproj
open macapp/Garage.xcodeproj
```

### Running a single test

The Rust tests are Cargo's: each crate's unit tests in `src/` and its integration tests in `tests/`.

```bash
cd rust
cargo test -p garage-ingest                              # one crate
cargo test -p garage-service --test postgres             # one integration test file
cargo test -p garage-service --lib schema                # the tests whose path matches
```

The Swift tests run only under Bazel, on a Mac (`aspect test //macapp/...`). The Aspect CLI takes
its own flags only. Pass each Bazel flag as `--bazel-flag=...`: a bare `--test_output=errors` is
rejected, and anything after `--` is read as a target pattern. There is no `aspect query`; use
`bazel query` (on `PATH` from `bazel_env`), e.g. `bazel query 'kind(codesign_test, //...)'`.

### Testing against Postgres

Most Rust tests need no database. The ones that do run against real Postgres + pgvector when
`GARAGE_TEST_DATABASE_URL` names a server, and pass without running when it is unset:

- `rust/garage-service/tests/postgres.rs`: the SQL only a server can judge: the migrations,
  applied and then re-applied; the per-model DDL, with each distance metric's operator class; the
  search query, including the halfvec and binary-quantized paths; the egress filter on pending
  chunks.
- `grpc.rs`, `ops.rs`, `facts.rs`, `clusters.rs` and `enrich.rs` beside it: the service over a
  socket and a port, the operations, the facts listing and the graph (its graph cases run only where
  the server has AGE: `apt install postgresql-16-age` on a Linux dev box; CI's image has none),
  clustering and fact enrichment.
- `rust/garage-cli/tests/cli.rs`: the end-to-end test. It runs the real `garage` and `garage-mcp`
  binaries, each as a child process, over the UI tests' fixture corpus
  (`macapp/Tests/Fixtures/corpus`): `init-db`, `register-model`, `add-source`, `scan`, `ingest`,
  `backfill`, `search`, then the MCP tools over stdio, with embeddings from a fake model server on
  loopback. Its assertions read the throwaway database directly.

Each run creates a throwaway `garage_test_*` database, applies `data/sql` to it and drops it;
nothing else on the server is touched. Put new tests that need real SQL there, and keep logic tests
on fakes.

- **Development Macs** run Homebrew PostgreSQL 18 with pgvector as a service. Use that server for
  every test except end-to-end app testing:

  ```bash
  brew install postgresql@18 pgvector
  brew services start postgresql@18
  echo 'export GARAGE_TEST_DATABASE_URL=postgresql://localhost:5432/postgres' >> .env   # direnv sources .env
  ```

  The URL needs a role that is a superuser, because pgvector is not a trusted extension and each
  run creates a database. Homebrew's cluster makes your login user one, with local trust auth.
- **Bazel** passes the variable through (`test --test_env=GARAGE_TEST_DATABASE_URL` in `.bazelrc`),
  so `aspect test //rust/...` uses the same server as `cargo test`.
- **Web sessions** get a server from the start hook (below).
- **The devcontainer** (`.devcontainer/`, built for the host's architecture) installs PostgreSQL 18 and
  pgvector from PGDG, starts the cluster on each container start (`start-postgres.sh`) with a
  `garage_dev` superuser, sets `GARAGE_TEST_DATABASE_URL` to it, and installs rustup, which reads
  `rust/rust-toolchain.toml`; `post-create.sh` builds the workspace once. From the host,
  `tools/e2e/devcontainer.sh` brings the container up and runs the CLI's end-to-end test and the
  service's database tests in it (other `cargo test` arguments replace those; `GARAGE_E2E_REBUILD=1`
  rebuilds the image). It needs Docker and the devcontainer CLI.
- **CI** runs them in the Linux `rust` job (`.github/workflows/ci.yaml`) against a
  `pgvector/pgvector` service container. The macOS Bazel job has no server, so they skip there.
- **Never point it at the app's own cluster.** The vendored Postgres (`//ext/postgres`, port 14824,
  password in the Keychain) holds the real corpus. It is for end-to-end app testing, the launchers,
  and the tests of the vendored build itself.

### CI

Every job that runs Bazel runs it through the Aspect CLI, set up by `aspect-build/setup-aspect`
(pinned by SHA). With the `ASPECT_API_TOKEN` org secret it signs the CLI in to Aspect Cloud (the
token on stdin, never in `GITHUB_ENV`), which wires Aspect's remote cache and BES into every
`aspect` task and plain `bazel` call, shared by all branches and jobs, and turns on the CLI's GitHub
features through Aspect's GitHub App: a check run per task, a PR summary comment, and lint findings
as review comments. A fork's pull request gets no secret and builds cold, without them. There is no
GitHub Actions disk cache and no BuildBuddy. `.aspect/config.axl` adds `--config=ci` on CI, and on a
Linux runner `--config=linux` after it, so Linux jobs target the host instead of ci's macOS platform.
Aspect ships no Windows CLI, so nothing on a Windows runner uses it.

- **`.github/workflows/ci.yaml`** runs on every push to `main` and `next` and every pull request;
  a newer push cancels an older run.
  - On Linux: `rust` (rustfmt, clippy, `cargo test` with a Postgres service, the protogen and
    cbindgen checks, the third-party notices check, the UniFFI Python round trip and the .NET
    binding's tests), `swiftcheck`, `winapp-bazel` (`aspect test //winapp/...`, the Windows app's
    projects but the WinUI app; see "Windows app") and `aspect`.
  - `aspect` runs the four Aspect CLI tasks (buildifier, format, gazelle, lint) in one Linux job.
    Each still reports its own `aspect / <task>` check, which the branch ruleset requires. Lint
    covers the Python dev tools that are Bazel targets (`//tools:third_party_notices`,
    `//winapp/bazel/...`), which need no Mac.
  - No job runs on macOS unless it needs a Mac, since macOS runners cost more and wait longer (Rick,
    2026-11-05), and checks share a job where they can, since each job waits for a runner and clones.
- **`.github/workflows/macos.yaml`** runs `aspect test //...` on macOS, building the app and the
  vendored Postgres, ICU and llama.cpp. Because it is slow:
  - pull requests run it only when build inputs change (see its `paths`);
  - `main` and `next` run it on every push, and `main` nightly;
  - a newer push waits for a running build instead of cancelling it.
  - Its cache is Aspect Cloud's; `--config=ci` uploads each local result as it finishes, so a run
    stopped by the timeout still leaves its work for the next. For CI only, setup-aspect's `bazelrc`
    adds `--build_tests_only`, `--noapple_generate_dsym`, no caching for the copy and codesign
    actions (their tree artifacts ran Bazel out of file descriptors) and the JVM's FD limit off.
- Run it by hand from the Actions tab (workflow_dispatch) when a change outside its `paths` needs
  the Bazel build.
- **`.github/workflows/pages.yaml`** builds the site with `aspect build //docs:site` (Jekyll 4 from
  `docs/Gemfile.lock` under rules_ruby, with the model catalog copied in) on pushes, and on pull
  requests that touch it; only `main` deploys it to GitHub Pages.
- **`.github/workflows/release.yaml`** publishes packages from a `v*` tag whose commit is on `main`,
  each by trusted publishing (OIDC, no stored token), in the `crates-io`, `pypi` and `rubygems`
  environments. The crates take the workspace's version (`rust/Cargo.toml`); the wheel and the gem
  take the app's release version (`rust/garage-rag`'s own `version`, and its `BUILD.bazel`'s, held by
  a test and the `check` job to GarageService's `VERSION`, which `garage --version` prints and the
  Windows installers read: bump the three together; it must stay above the
  pure-Python 1.5.0 on PyPI). A version a registry already has is skipped.
  - crates.io: every crate whose `publish` is not false (the workspace default is false, so a crate
    opts in), with `cargo publish --workspace`. crates.io trusts a publisher only for an existing
    crate: publish a crate's first version by hand, then add the workflow as its trusted publisher.
  - PyPI and RubyGems: `garage_rag`, the umbrella of the UniFFI crates (`rust/garage-rag`, one
    cdylib, one module per namespace): maturin wheels and platform gems (`ruby/build.sh`) for macOS
    arm64, Linux x86-64 and arm64 (manylinux_2_28), and Windows x64, each tested with a round trip
    (and the wheel's `garage --version`) before upload. libgit2 is linked statically, built from its
    pin by `tools/wheels/build_libgit2.sh` (vcpkg's on Windows). The PyPI project's trusted publisher
    must name `release.yaml` and the `pypi` environment.
- **`.github/workflows/windows.yaml`** builds Postgres (with pgvector, ICU and zlib) from source on
  `windows-latest`, from the pins in `ext/*/*.MODULE.bazel` (read by `tools/windows/fetch_ext.py`),
  with each project's own MSVC build rather than Bazel; the three Rust service libraries with Cargo
  for MSVC; then the Windows app and its tests on both, and the installers (`package`).
- **`.github/workflows/known-answers.yaml`** (on changes under `ext/llama_cpp`, `ext/nomic_embed`,
  `tools/llama`) rebuilds `llama-embedding` and regenerates the nomic-embed Q2_K reference vectors
  (`tools/llama/known_answers.py`). The reference is the Apple silicon CPU job; Metal and a Linux
  x86-64 job are held to `MIN_COSINE` (0.98) against it, because Q2_K is not bit-exact across
  backends or ISAs: Metal measured 0.988 at worst and x86-64 about 0.99. LlamaXPCService's "Embedding
  Known Answers" self-test and `//macapp/Tests/LlamaEngineTests` compare `LlamaCppEngine` against the
  reference (`LlamaKnownAnswers`). The reference, `ext/nomic_embed/known_answers.json`, is not
  committed yet: commit the macOS CPU job's `known-answers-macos-cpu` artifact (or the output of
  `tools/llama/gen_known_answers.sh` on an Apple silicon Mac); until then both skip.
- `.mcp.json` registers `aspect mcp` for Claude Code: read-only tools over the builds CI sends to Aspect
  Cloud (invocations, build logs, targets, action history). It needs the `aspect` CLI on `PATH` and a
  signed-in CLI (`aspect auth login` once); signed in, `aspect build //... --remote` also uses Aspect's cache.
  Aspect Cloud needs CLI 2026.41.24 or newer (`.aspect/version.axl`).

### Rust (`rust/`) and reader plugins

Every component was ported from the Python package one at a time
([docs/plans/rust-plugins.md](docs/plans/rust-plugins.md), [docs/plans/python-removal.md](docs/plans/python-removal.md));
the Python modules named below are the originals each crate ports, kept for reading the history.
`rust/` is a Cargo workspace (toolchain pinned in `rust-toolchain.toml`, the same as MODULE.bazel's) that
Bazel also builds through rules_rs (`crate.from_cargo` over `rust/Cargo.lock`; each crate's `BUILD.bazel`
mirrors its `Cargo.toml` by hand, and gazelle leaves the folder alone). On Linux, `.bazelrc`'s `build:linux`
uses `//bazel:linux_gnu`, the host plus a libc constraint the Rust toolchains need. On macOS, `build:macos`
turns rustc's stripping off (`-Cstrip=none`): macOS 27's dyld rejects what rust-objcopy strips.

- **The contract.** `proto/garage_plugin.proto` (`garage.plugin.v1.ExtractorPlugin`: `Describe`, `Extract`)
  is between the ingester and its readers: a file name and bytes in, never a path. It crosses gRPC on a
  Unix-domain socket (a plugin in its own process) and a C ABI over the serialized messages (a reader
  linked in). `rust/garage-plugin` has both sides; its generated code is checked in, made by
  `cargo run -p protogen` (needs `protoc`) after editing the proto, and CI fails when it is stale.
- **The text reader** (`rust/garage-text`) ports `extract/text.py`; `garage-text-plugin` serves it over
  gRPC and `garage-text-ffi` exports it (`include/garage_text.h`).
- **The embed worker** (`rust/garage-embed`) ports `ops/backfill.py` over the GarageService facade
  (`ListModels`, `GetEmbeddingBatches`, `UpdateEmbeddings`, `BackfillDistilled`, through `rust/garage-facade`,
  the blocking GarageService client every worker shares, generated by `protogen` from `garage.proto` too), with the same events and messages. It sends nothing itself: its host
  carries each model-server request (`Host::http`; `llama_xpc` may go over NSXPC) after the worker's
  `egress` module, a port of `net/egress.py`'s destination rules, has approved it. `garage-embed-ffi`
  exports it as JSON over a C ABI (`include/garage_embed.h`). With
  `"settings": "service"` it reads the backend's own `embedding.*` through `GetSetting`. GarageEmbedXPCService
  runs it (`macapp/Sources/GarageEmbedWorker` is the Swift host: llama_xpc over NSXPC, Ollama and LM Studio
  over a proxy-less URLSession that returns redirects, image models over NSXPC), and the app's Backfill goes
  there (`EmbedClient`), not to the backend's `Backfill` RPC, which the CLI uses.
- **Ingest** (`rust/garage-ingest`) ports the pipeline a piece at a time: so far the walker (`ingest/walker.py`,
  its rules as data in `WalkPolicy`, held to Python's tables), the quality gate (`extract/quality.py`, with
  Python's `str` character classes so every metric matches), chunking (`ingest/chunking.py` over
  `ingest/splitters.py`, with `re`'s reading of the separator tables, so chunks, ids and offsets match) and
  materializing placeholders (`ingest/materialize.py`: the budget, the timed-out reads it bounds and the
  dataless-file I/O policy, `setiopolicy_np` bound at link time) and attribution (`attribute/resolver.py` and
  `pathrules.py`, with `email.utils.parseaddr` ported for senders) with git history read through libgit2
  (`rust/garage-git`, the three reads `_garage_git` makes, bound by hand with no `git2` crate: Bazel links
  `//ext/libgit2`, Cargo finds it with `pkg-config` or `GARAGE_LIBGIT2_DIR`, so a Cargo build needs libgit2
  installed; with its tests held to what `git` reports) and the per-file decisions of
  the loop (`ingest/pipeline.py`'s `ingest_one`, behind `FileHost` and `Storage` traits, with
  `extract/contact_names.py` for authors' names) and the loop over a walked source (`_ingest_source`, in
  `source.rs`; a Messages source is read thread by thread in `conversations.rs`, the glue of
  `ingest/conversations.py` over the FOSS `messages-markdown` crate (crates.io, from
  `lwm-luminx/markdown-extract`, which bundles its own SQLite)) and the scanners that count a source first
  (`ingest/scanner.py`, in `scanner.rs`: feeds read as expat would, in `feed.rs`, and databases through the
  system's SQLite, bound by hand in `sqlite.rs`, so a Cargo build on Linux needs `libsqlite3-dev`), persisting through `GrpcStorage` (`facade.rs`, the `GrpcIngestStorageGateway` port:
  `BeginIngestSession`, `PersistScan`, `CheckDocumentStat`, one `PersistDocument` per call and
  `FinalizeIngestSession`). `garage-ingest-ffi`
  exports them as JSON over a C ABI (`include/garage_ingest.h`). `garage_ingest_run_source` runs a whole source,
  with each file's text read through a host callback when the host asks for that (for a Messages source the host
  gives only the names contacts shared). `garage_ingest_run` is the service's whole run, `ingest_xpc`'s port: one
  source or every enabled one (`"*"`, `ListSources`), the settings GarageService runs with (`"settings":
  "service"`, over `GetSetting`) and the app's `IngestProgress` events field for field. With `"readers": {...}`
  (`extraction.*`, also read over `GetSetting`) either run reads every file itself with `rust/garage-readers`: `extract/dispatch.py`'s routes over garage-text,
  the FOSS `mail-markdown`, `pdf-markdown` and `office-markdown` crates and garage-ocr (Vision on the Mac,
  Tesseract elsewhere, `extract/image.py`'s policy), plus `extract/nicknames.py`'s shared names (rusqlite and
  `plist`). Mail, PDF, Office and pictures are new readers with their own revisions, so each such file is read
  again once; `CheckDocumentStat` and the no-text and failed `PersistDocument`s carry the reader's revision
  (`extractor_revision`), which GarageService remembers. `extraction.plugins` does not apply to the Rust readers yet. GarageIngestXPCService runs it (`GarageIngestRunner`, linked
  statically) with the Rust readers. The service is built on GarageXPCKit alone
  and needs GarageService's socket or port; with neither an ingest fails.
- **The MCP server** (`rust/garage-mcp`) ports `mcp_server/` with no search or database code: it reads
  the corpus through GarageService's `Corpus*` calls, whose handlers run the tools' own functions
  and return their results as JSON, each carrying a `CorpusCaller` for the access hooks. It ports the
  protocol, pydantic's argument errors, `rag_ask`/`rag_generate`/`rag_agent` (the local model through
  `garage-embed`'s host and egress rules) and the streamable HTTP transport (GET answers 405).
  `garage-mcp-ffi` is its C ABI (`include/garage_mcp.h`). GarageMCPServerService runs
  it on GarageXPCKit (`GarageMCPRustServer`), and the stdio `garage-mcp` launcher runs it in-process (`rust/garage-cli`, below).
- **The backend** (`rust/garage-service`, [docs/plans/python-removal.md](docs/plans/python-removal.md)) ports
  `garage_rag/service` (GarageService over tokio-postgres + deadpool) one stage at a time: so far the database
  layer (`db.rs`, the app's socket URL), `garage.json` (`config.rs`, `SECTIONS` as data), the migrations, the model
  registry and per-model DDL, the embed facade (`GetEmbeddingBatches`, `UpdateEmbeddings`, `BackfillDistilled`), the
  ingest facade (`BeginIngestSession` through `FinalizeIngestSession`, `gateway.rs`), hybrid search, the five
  `Corpus*` reads with the MCP tools' JSON, `Ping`/`GetStatus`/`GetVersion`/`Search`/`ListDocuments`/
  `GetDocument`/`ListSources`/`ListModels`/`GetStats`/`GetSetting`/`InitDb`, `service/auth.py`'s token and
  socket rules, and the operations (`ops/sources.py`, `ops/models.py`, `ops/settings.py`, `ops/mcp.py`,
  `ingest/reconcile.py`): `AddSource`/`RemoveSource`/`SyncSources`/`ImportSourcesToConfig`/`Reconcile`
  (`sources.rs`), `Scan` streaming `garage-ingest`'s scanners, `RegisterModel` over `models.json`
  (`catalog.rs`)/`SetDefaultModel`/`DropModel`/`EmbedText`, `SetSetting` (the file rewritten in `config init`'s
  layout and the process reloaded from it, `config.rs`) and `McpInstall`/`McpUninstall`/`McpStatus`
  (`mcp_install.rs`), each with the Python message; the Facts page's reads (`ops/facts.py`: `ListFacts`/`GetFactStats`,
  `facts.rs`; `ListFactPrompts` over `config/fact_prompts.py`'s merge and hashes, `prompts.rs`, which also validates
  `facts.prompts`) and the AGE projection with its three reads (`db/graph.py`: `rebuild_graph`, `GetGraphLabels`/
  `FindGraphVertices`/`GetGraphNeighborhood`, `graph.rs`; `available = false` without AGE or a built graph) and
  `ClusterFacts` (`enrich/clusters.py` step for step in `clusters.rs`: the guard, both levels, anchors, the distiller over
  `garage_mcp::chat` run in `spawn_blocking`, one transaction, progress streamed; `tests/clusters.rs`) and
  `EnrichFacts` (`enrich/facts.py`, `enrich/metadata.py` and `ops/facts.py`'s loop in `enrich.rs`: the metadata facts
  with no model, `fact_runs` and `stale_only`, the egress rule per document, each prompt's facts replaced in their
  own transaction, `tests/enrich.rs`; the model's side is a `FactExtractor`: `langextract.rs`'s `LangExtractor`,
  the langextract-rs crate (crates.io; prompting, parsing and alignment, no I/O of its own) over `garage_mcp::chat`'s
  `ChatModel` on `facts.provider`'s local server, each prompt sent through the host after the document's class
  passed `check_egress`, which the serve binary, `garage-service-ffi` and the CLI's in-process service set with
  `with_extractor`; a service without one writes the metadata facts and fails each prompt as unavailable), `EnsureLlamaModel` through the host's loader (`FAILED_PRECONDITION` outside the app) and `Backfill` (`ops/backfill.py`: `garage-embed`'s worker run in-process over `LocalFacade`, the pool answering its facade calls, with its progress streamed, `backfill.rs`), so every RPC of `garage.proto` is answered.
  `garage-service serve` is the binary (`--socket` or `--host`/`--port`, `GARAGE_GRPC_*`). `tests/postgres.rs` holds
  the SQL to a server, `tests/grpc.rs` the service over a socket and a port and
  `tests/ops.rs` the operations over gRPC and `tests/facts.rs` the facts listing and the graph (its graph cases run
  only where the server has AGE: `apt install postgresql-16-age` on a Linux dev box; CI's image has none); all need
  `GARAGE_TEST_DATABASE_URL` and pass without running when it is unset (CI's rust job has a pgvector service). The query embedder goes through `garage-embed`'s providers
  and egress rules; the binary's host speaks plain HTTP only. `garage-service-ffi` is the service behind a C ABI
  (`include/garage_service.h`: `garage_service_start`/`is_running`/`stop`, a database `probe` for the self test, and
  a `GarageServiceHost` of the embed worker's shape for the model servers and image models); GarageXPCService runs
  it (`GarageRustService`, on GarageXPCKit, with `GarageEmbedWorkerHost` carrying the host calls), on the
  `garage.json` in the app's working directory and the bundled schema (`GARAGE_SQL_DIR`).
- **The command line** (`rust/garage-cli`) ports `cli.py`: every `garage` command (the `config`, `facts` and `graph`
  groups included) and the `garage-mcp` stdio server, with Typer's usage errors, Rich's tables and markup (plain
  off a terminal) and the messages the Python CLI printed. A command runs GarageService in its own process, on a private
  owner-only socket under `$TMPDIR`, and calls it through `garage-facade`, so the CLI needs no running app:
  `ingest` runs `garage_ingest_run` with the Rust readers persisting through that socket, `ask` and `mcp-test` call
  `garage-mcp`'s toolbox directly, `mcp-serve` runs its HTTP server (`--sse` is retired), and `serve` is
  `garage-service serve`. `config schema` prints the JSON Schema of `garage.json` from the settings table
  (`garage-service`'s `schema` module) and `--publish` writes `docs/.data/garage.schema.json`, which a test holds
  to the generator. The `garage` and `garage-mcp` binaries are the crate's; `libgarage_cli.a` exports `garage_cli_main`/`garage_mcp_main` (`include/garage_cli.h`)
  for the Mac app's launcher helpers, which link it statically (`macapp/Sources/GarageLauncher`).
  `tests/cli.rs` runs both binaries over the fixture corpus against a throwaway database (`GARAGE_TEST_DATABASE_URL`).
- **C headers.** The FFI crates' `include/*.h` are generated from their Rust by cbindgen: `cargo run -p headergen`
  rewrites them (each crate's `cbindgen.toml` holds the prologue and renames; the Rust doc comments become the
  header's), and CI's `headergen -- --check` fails when one is stale. Edit the Rust, never the header. So far
  `garage-cli`, `garage-text-ffi`, `garage-embed-ffi` and `garage-service-ffi`; add a crate to `CRATES` in
  `rust/headergen/src/main.rs`.
- **UniFFI** (pilot, [docs/plans/uniffi.md](docs/plans/uniffi.md)): `rust/garage-embed-uniffi` is the embed worker

### Swift app dev loop

The app is built by Bazel only; there is no SwiftPM manifest. The Swift modules depend on the Rust
static libraries (`rust/*-ffi`, built through rules_rs), which SwiftPM cannot provide.

```bash
aspect build //:macapp     # the .app, with Postgres + pgvector and llama.cpp built from ext/ and the Rust libraries linked in
aspect run //:xcodeproj    # generate macapp/Garage.xcodeproj for iterating in Xcode
open macapp/Garage.xcodeproj
```

See `macapp/README.md` for why Postgres can't just use the Homebrew build (it bakes absolute
`/opt/homebrew` paths).

The bundled Postgres is one package, `//ext/postgres`, built from 18 (the default) or the 19 beta:
`--//ext:postgres_version=19` (or `--config=pg19`) switches its source between the `@postgres` and
`@postgres19` repositories (`postgres.MODULE.bazel`, `postgres19.MODULE.bazel`), as `//ext/age` switches
AGE's release line. Everything downstream depends on the `//ext:postgres`/`postgres_rpath`/`libpq`/
`libpq_dylib` aliases. Each major's patches live in `ext/postgres/pg<major>/`, the same two for both:
`appstore.patch` (adds `--enable-appstore`, off by default upstream and passed by our build: a flock()
interlock on the data directory instead of the System V shim segment, and pthread semaphores in the
mmap'd segment; the 19 copy is ported to 19's `PGSemaphoreShmemRequest` API and matches the series
proposed upstream against master) and `username.patch` (the local getpwuid() workaround, not for
upstream). A change to one major's patch needs porting to the other.

Apache AGE (`//ext/age`, graph queries in openCypher) is built beside pgvector, from the AGE release
line matching the selected major (`ext/age/pg18`, `ext/age/pg19`). `001_extensions.sql` creates it
only where the server has it installed, so Homebrew and the CI image, which lack it, still migrate.

Without a Swift toolchain (Linux, Claude Code on the web) there is still a syntax gate:

```bash
tools/swiftcheck/check.sh                                # swiftc -parse when swiftc is on PATH, else tree-sitter
python tools/swiftcheck/swift_syntax_check.py            # the tree-sitter checker directly
```

`check.sh` prefers a real `swiftc -parse` over every `macapp/**/*.swift` (plus `swift-format lint`
when installed) and otherwise falls back to the tree-sitter parser, which reports unbalanced
braces, malformed closures/attributes and stray tokens with line numbers but knows nothing about
types or modules. Valid constructs the grammar cannot parse live in `tools/swiftcheck/baseline.txt`
and are ignored; a new problem fails the check. The tree-sitter checker needs `tree-sitter` and
`tree-sitter-swift`, in the venv `GARAGE_SWIFTCHECK_VENV` names (default `.swiftcheck-venv`). Run it
after every Swift edit made without a full build; the real compile is still `aspect build //:macapp`
on a Mac.

Web sessions get both from `.claude/hooks/session-start.sh` (registered in `.claude/settings.json`,
runs only when `CLAUDE_CODE_REMOTE=true`): it creates `.swiftcheck-venv` with `uv` and downloads a

`GARAGE_SWIFT_SHA256`). The download needs `download.swift.org` allowed in the environment's network
policy; when it is not, the hook says so and the tree-sitter fallback still runs.

The hook also starts the image's Postgres for the Rust tests that need a server. If the
distribution's pgvector predates 0.7, which added `halfvec` and `binary_quantize`, it builds pgvector
from source; override the version with `GARAGE_PGVECTOR_VERSION` (default 0.8.1). It creates a

when any step fails, the hook says so and those tests pass without running.

## Architecture

### Ingestion pipeline (`rust/garage-ingest`, `garage-readers`, `garage-service`)

```
sources ──▶ walker ──▶ [materialize] ──▶ extract ──▶ quality gate
                                                          │
                            attribution ◀─────────────────┤
                                  │                       ▼
                                  └──────▶ documents ── chunks
                                                          │
                                              ┌───────────┴───────────┐
                                              ▼                       ▼
                                         emb_<model_1>           emb_<model_2>
                                              └───────────┬───────────┘
                                                          ▼
                                              hybrid search (RRF)
                                                          │
                                                    MCP server
```

The module names in this section are the Python originals each Rust piece ports (the "Rust" section
above maps them to crates); the Rust code keeps their names in its docs.

- **Walk** (`ingest/walker.py`, `garage-ingest`'s `walker`) — stats candidates without opening them;
  pruning happens during descent so excluded subtrees are never entered.
- **Materialize** (`ingest/materialize.py`) — cloud placeholder files (Dropbox and iCloud online-only
  stubs; dataless under File Provider) download when read, so this is budget-metered
  (`MaterializationBudget`), and on macOS the dataless-file I/O policy is off for the pipeline's
  thread so only the materialize thread can start a download. Idempotent ingest means hitting the
  budget cap is fine, not a failure.
- **Extract** (`rust/garage-readers`, `extract/dispatch.py`'s routes) — dispatch by extension:
  Markdown and code verbatim through `garage-text`; PDF, Office and mail (`.eml`/`.emlx`, filed as
  `communication`) through the FOSS `pdf-markdown`, `office-markdown` and `mail-markdown` crates
  (`lwm-luminx/markdown-extract`); pictures through `garage-ocr`, Vision on the Mac and Tesseract
  elsewhere (`extract/image.py`'s policy; no Tesseract on Windows yet, so pictures read as no text
  there). Messages `chat.db` (`sqlite` sources) is not walked file
  by file: `conversations.rs` (over the `messages-markdown` crate) stores each thread as one document with one chunk per message,
  each carrying `chunks.direction` (`sent`/`received`) and `chunks.sender` (`014_chunk_direction.sql`) for
  search's `direction` filter; messages in no `chat_message_join` row join their sender's one-to-one chat.
- **Quality gate** (`extract/quality.py`) — content-based backstop against non-prose text (repeated
  line shapes, timestamp prefixes, hex/base64 density) that path rules alone miss.
- **Attribute** (`attribute/`) — precedence-ordered signals, each recording its `evidence`: git
  history (`git.py`, one pass over each repo's history, not one per file) → embedded document
  metadata (filtered through `looks_like_tool_name` so `python-pptx`/`openpyxl` don't self-attribute)
  → path convention (`pathrules.py`, data-driven table) → source default. A mail message is
  attributed by its sender instead of by metadata (the owner's name or address → `authored`, anyone
  else → `received`); a Messages thread records its handles as `sender`/`recipient`. See
  `docs/attribution.md`. History, the origin URL and the tracked-file count are read in-process through
  libgit2, never by running `git`: `rust/garage-git` binds the three reads by hand, with `//ext/libgit2`
  (1.9, no HTTPS or SSH transport) linked statically in the app, so nothing is loaded at run time; its
  tests hold it to what `git` reports.
- **Store** — chunks are model-agnostic; see the schema section below.
- **Distill facts** (`enrich/facts.py`, `garage-service`'s `enrich.rs`, `garage enrich-facts`,
  `EnrichFacts` RPC) — optional post-ingest pass: LangExtract's extraction loop (the FOSS Rust port
  `lwm-luminx/langextract-rs`, behind the `FactExtractor` trait), driven through Garage's own local
  model client against the local server `facts.provider` names, distills each document into atomic, span-grounded `facts` rows; every
  fact also gets its own `chunks` row (`chunks.fact_id`, `chunker = 'facts:...'`), so the ordinary
  backfill embeds facts under every model with no fact-specific path. The prompts are
  configurable (`facts.prompts`, more than one). Schema in `data/sql/006_facts.sql` /
  `007_chunk_fact_link.sql` / `013_fact_prompts.sql`.
- **Distilled facts** (`enrich/clusters.py`, `garage cluster-facts`, `ClusterFacts` RPC) — those
  facts are *potential* facts. The pass links each one to a `distilled_facts` row
  (`facts.distilled_fact_id`, `015_distilled_facts.sql`, `016_fact_dedup.sql`) in two levels:
  - Per document, restatements point at a representative (`facts.restates_fact_id`).
  - Across the corpus, representatives are grouped by growing each group from a tight seed until a
    neighbour is too far from the centroid or pulls it too far from the seed; groups record
    `spread`/`radius`/`drift`. Incremental runs attach new facts to stored centroids; `--full` (or
    a changed `facts.cluster_*` grouping setting) regroups, keeping rows whose members are unchanged.
  - Metadata is ground truth: `enrich-facts` writes a mail's sender/recipients/subject and a thread's
    participants as facts with no model (`enrich/metadata.py`, `extractor = 'metadata'`). Each distinct
    value is an anchored distilled fact (`anchor_key`, `018_fact_anchors.sql`) with a fixed centroid;
    inferred facts of its class join it first, without moving it.
  - A numbers/dates/negation guard applies at both levels. The local chat model confirms each
    loose group and states it once; a tight one is kept as is.
  - Each model's `fact_emb_<slug>` table (made with the model) holds distilled-fact vectors: the
    clustering model's centroid and `seed`, and under other models the mean the backfill writes.
  - Where AGE exists, `db/graph.py` (`garage graph rebuild`) projects Document, Chunk, Author,
    PotentialFact and Fact vertices into the graph `garage`. A prompt's `graph` block
    (`facts.prompts[].graph`) adds vertex labels per class and edges from relation classes, so new
    vertex and edge types are config (`graph_schema`, `projection`). The same module reads it back
    over AGE's label tables with bound parameters, never Cypher built from input: labels with counts,
    a title search and a breadth-first neighbourhood walk with label filters (`GetGraphLabels`,
    `FindGraphVertices`, `GetGraphNeighborhood`; `garage graph labels|find|neighbors`). Labels come
    from the catalog, so a configured label needs no change there, and its vertices are searched by
    their `title` property. The app's Graph page (`Views/GraphView.swift`, radial layout in
    `GraphLayout.swift`) draws one vertex's neighbourhood; the Facts and Documents pages link into it
    with Show in Graph.
- **Local inference** (`garage-embed`'s providers, `inference/`) — the one client for
  LM Studio, Ollama and the app's `LlamaXPCService`: embeddings, chat and model listing on the
  OpenAI-compatible `/v1` routes (Ollama embeddings stay on `/api/embed`), plus LM Studio model
  management on its native `/api/v1` REST API. The worker sends nothing itself: its host carries each
  request (`Host::http`; `llama_xpc` over NSXPC in the app) after the `egress` module has approved
  it: loopback or the configured host, `llama_xpc` loopback only, and a communication never to a host
  that is not loopback. A 2xx reply whose body is `{"error": ...}` is an error (LM Studio answers
  unknown routes that way).
- **Search** (`search/hybrid.py`, `garage-service`'s `search.rs`) — Reciprocal Rank Fusion over pgvector KNN and Postgres FTS
  (`k=60`, 200 candidates/engine). Keyword side ORs terms rather than ANDing, favoring recall since
  RRF (not the keyword match itself) decides final ordering.
- **Serve** (`rust/garage-mcp`, `mcp_server/server.py`) — MCP 2.0 over stdio or local HTTP. Every tool
  returns a typed record so MCP 2.0 maps it field-for-field instead of wrapping scalars in
  `{"result": ...}`.
- **gRPC bridge** (`rust/garage-service`, `proto/garage.proto`) — the `GarageService` the apps'
  Search and Documents views read through, and the database facade the ingest loop (`GrpcStorage`)
  and the embed worker persist through. Handlers translate proto messages to and from the operations
  the CLI also calls (`sources.rs`, `models.rs`, `mcp_install.rs`, ...: the CLI command and the RPC
  are both thin presenters over one function), with `ServiceError` mapped onto gRPC status codes. Long jobs
  (`Backfill`, `EnrichFacts`) are server-streaming; cancelling the call stops the work at its next
  progress step. The server accepts requests up to 256 MiB (`MAX_REQUEST_BYTES`), since
  `PersistDocument` carries a whole document's text and chunks. When `GARAGE_GRPC_TOKEN` is set (the
  app sets a random one per launch, passed like `GARAGE_GRPC_PORT` and never logged or saved), every
  call but `EnsureLlamaModel` must carry it as `x-garage-token` metadata or gets `UNAUTHENTICATED`
  (`auth.rs`; `garage-facade` and the app's `GarageGRPCAuth` send it). Without a token, the
  config-changing methods (sources, models, `SetSetting`, MCP install/uninstall, and `InitDb`, whose
  `schema_dir` names SQL to run) are answered only by a server bound to the Unix socket; a server on a
  TCP port gives `PERMISSION_DENIED`, since `SetSetting embedding.ollama_host` widens egress.

- **Access hooks** (`rust/garage-access`, [docs/plans/access-hooks.md](docs/plans/access-hooks.md)) — every
  corpus read names its `Caller` (the app, `garage`, or an MCP client from `CorpusCaller`) and asks the
  build's `AccessPolicy` for a `SqlFilter` over `d`/`s`, which goes inside the read's own `WHERE`. Garage
  ships no policy: a plain build links `rust/garage-access-none` as `garage_access_extension`, and a build
  with one sets the label flag `//rust/garage-access:extension` (garage-enterprise does). A new
  GarageService method must be placed in `READ_PATHS` (`garage-service/src/access.rs`), or its test fails.

Two independent hashes drive idempotency: `source_sha256` (raw bytes — skip unopened) and
`content_sha256` (extracted text — rebuild chunks when an extractor improves). One DB transaction
per document. An unchanged stat skips a file before it is read (`CheckDocumentStat` over the facade);
a file with no text (empty, whitespace, a textless image) gets no document, and it and a failed
extraction are remembered in `ingest_outcomes` (`012_ingest_outcomes.sql`) until the file or its
extractor's `VERSION` changes. Replacing a document keeps every chunk whose `ord`, hash, text and
chunker are unchanged, so its vectors survive and backfill re-embeds only what changed.

Full detail: `docs/architecture.md`.

### Database model (DDL in `data/sql/00*.sql`)

`data/sql/00*.sql` is the schema source of truth (CHECK constraints, generated `tsvector`), applied
by `garage-service`'s `migrate.rs`. Migrations are idempotent
(`IF NOT EXISTS` / `duplicate_object` guards) and are meant to be re-applied, not tracked as a
linear history.

Two independent axes on every document:

- `corpus_class` — **what it is**: `document` | `code` | `communication` (communications never
  leave the machine — this is what the egress guard's content rule keys on, not trust. MCP clients still
  receive whatever excerpts they retrieve, communications included; see `docs/privacy.md`).
- `trust_tier` — **how much it's trusted**: `authored` | `reference` | `received`.

Embeddings live one table per model (`emb_<slug>`, e.g. `emb_bge_m3`) rather than one shared table,
because different models have different vector widths and pgvector can't share a column across
them. `chunk_id` is both primary key and `ON DELETE CASCADE` FK back to `chunks`, so deleting a
chunk removes its vectors from every model table atomically — re-indexing onto a new model is a
backfill, not a re-ingest. Potential facts' vectors sit beside it in `potential_fact_emb_<slug>`
(keyed on `fact_id`, `017_fact_vectors.sql`; the backfill routes a fact chunk's vector there), so
facts and passages each have their own index; search's vector side unions the two. Storage type is selected by dimension against pgvector 0.8 HNSW ceilings
(`vector` ≤2000 dims, `halfvec` ≤4000, binary-quantized beyond that for non-MRL models). Full
reference: `docs/schema.md`.

### Privacy guarantee: one egress choke point, an allowlist, and communications stay local

Content goes only to approved destinations, and communications never leave the machine. Each layer
has tests of its own (`rust/garage-embed/src/egress.rs`, `tests/test_embed_egress` in the worker,
`garage-service/tests/postgres.rs`'s egress filter), so removing one fails the suite:

1. **One choke point.** No Rust crate of the pipeline opens an outbound connection itself: the embed
   worker, the fact distiller, the query embedder and the MCP server's `rag_ask` hand each model-server
   request to their host (`garage-embed`'s `Host::http`), and only after `garage-embed`'s `egress`
   module, the port of `net/egress.py`'s destination rules, has approved it. The hosts (the Mac's
   XPC services, `Garage.Services.exe`, the CLI's own host) speak plain HTTP to that one destination,
   ignore proxy variables and never follow redirects.
2. **No cloud AI SDK** anywhere (`anthropic`, `openai`, `google.genai`, ...), and none in `Cargo.lock`.
   OCR is Vision or Tesseract, on the machine.
3. **Destination allowlist.** `egress::check_destination` approves loopback and exactly the origins
   configured as `embedding.ollama_host` / `embedding.lmstudio_host` (which may be off-box), and
   refuses anything else. There is no free-form extra-hosts setting. `llama_host` must be loopback.
4. **Content rule.** `corpus_class = 'communication'` never goes to a destination that is not
   loopback: `check_destination(..., corpus_class)` checks it before anything else, fact
   extraction and `rag_ask` pass the class, and the backfill asks `egress::allows_communications` and
   withholds communication chunks from an off-box provider (the egress filter on pending chunks).
5. **Local fact extraction.** The fact distiller runs only on the local servers `facts.provider`
   names, and refuses a cloud model id.

When touching `garage-embed`'s `egress` or providers, the service's enrichment, or anything that
could construct an outbound request for document content, preserve all of this — it's the
load-bearing privacy property of the project. A new caller takes its host from the embed worker's
and goes through `check_destination`. Full detail: `docs/privacy.md`.

### Local endpoints: sockets and XPC peers

Postgres, the `GarageService` gRPC facade and LlamaXPCService's llama-server API listen on Unix-domain
sockets in `s/` at the root of the App Group container (0700; `GarageSockets` in `GarageXPCKit`),
not on loopback TCP, which every account on the Mac can reach. The Rust pieces find them through the
database URL (`?host=<dir>&port=14824`), `GARAGE_GRPC_SOCKET` and `GARAGE_LLAMA_SOCKET`, which the
app's XPC services and the launchers set; an endpoint whose socket path would overflow `sun_path`
(104 bytes) keeps its old port. Every XPC service requires its peers to be signed by its own team
(`GarageXPCPeerRequirement`), and the embed worker's `llama_xpc` requests go over NSXPC through its
Swift host (`GarageEmbedWorkerHost`). See `docs/privacy.md`.

### Configuration (`rust/garage-service/src/config.rs`)

One JSON config, nested on disk (`~/.garage.json`, or `./garage.json` for project-local override,
or `--config PATH`) but read flat by the code. `SECTIONS` is the single table that knows both
shapes, each setting's type, default and description, and drives loading, saving, `GetSetting`/
`SetSetting` and schema generation together so they can't drift. Unknown keys are a hard error, not a
silent ignore (retired keys listed in `RETIRED_KEYS` are warned about and skipped). The JSON Schema is
generated from that table (`garage config schema --publish`, `schema.rs`) and committed at
`docs/.data/garage.schema.json`, which the site serves as
`https://garagerag.app/.data/garage.schema.json` (every config's `$schema`) — **regenerate it whenever a
setting is added, renamed, or documented**; a test holds the committed file to the generator and
checks that every setting is documented. The `facts` section (`facts.model`, `facts.provider`:
`llama_xpc` | `ollama` | `lmstudio`) names the model behind `enrich-facts`, and `inference.model` /
`inference.provider` the one behind the `rag_ask`/`rag_generate` MCP tools (empty: the facts model
answers); `garage config set SECTION.KEY VALUE` / `garage config get SECTION.KEY` edit and read single
settings without touching the JSON by hand. `facts.prompts` (`prompts.rs`) lists named LangExtract
prompts, merged by name with the built-in `default`; `enrich-facts` runs every enabled one (or
`--prompt NAME`), each fact records its `prompt_name`/`prompt_sha256`, and `fact_runs`
(`data/sql/013_fact_prompts.sql`) backs `--stale-only`.

### macOS app (`macapp/`)

- `PostgresService` owns a private, relocatable Postgres cluster (built from source — see
  `macapp/README.md` for why Homebrew's build won't work) in `pgdata/` of the data folder.
- The data folder (`pgdata`, `models`, `logs`, `garage.json`) is `Library/Application Support/GarageApp`
  in the App Group container, `Library/Group Containers/DWVXMLB45Y.group.me.rickmark.garage-rag/Library/Application Support/GarageApp` under the home folder, so the App Store and Developer ID
  builds share one corpus. Both sign the app and its seven XPC services with the team-prefixed group
  (`GarageAppGroup` in `GarageXPCKit`); the Developer ID app adds its application identifier
  and team identifier, backed by the Developer ID provisioning profile garage-enterprise embeds
  (`macapp/Sources/GarageApp/GarageDeveloperID.entitlements`), while its XPC services carry only
  the group (`macapp/externals/GarageAppGroup.entitlements`). Unentitled builds (locally signed,
  tests) use `~/Library/Application Support/GarageApp`.
- The Postgres password is a generic-password item in the data-protection keychain, access group
  = the App Group (`GaragePostgresEndpoint` in `GarageXPCKit`: read, save, and the migration
  of the old login-keychain item, which the app runs off the main actor before its first read and
  which copies the item, leaving it for pre-1.5 builds). Any process entitled
  to the group with a profile-backed application identifier reads it without a prompt; a process
  without one (ad-hoc, `local_signed`) gets `errSecMissingEntitlement` and falls back to the login
  keychain, so local builds work as before. `macapp/README.md` ("The Postgres password") has the
  details.
- At launch `GarageDataMigration` renames an older build's per-user folder into the group
  container and leaves a symlink behind. It never copies, deletes or overwrites anything, and it skips a `pgdata` a running postmaster still holds. Unsandboxed
  (Developer ID) builds also keep `~/Library/Application Support/GarageApp` as a link to the group
  folder on a fresh install, so the familiar path reaches the data; a folder or other link already
  there is left alone.
- "Reset Database" (`DatabaseResetSheet` → `AppState.resetDatabaseAndRelaunch`) stops every
  service, deletes `pgdata` and relaunches the app with `--after-database-reset <old pid>`, also left in
  the app's defaults (`GarageRelaunchHandoff`, read through `GarageAppLaunch.arguments`) because the sandbox
  drops a relaunch's arguments. The old
  instance then quits at once (`hasHandedOffToRelaunch`: `.terminateNow`, and no quit-time shutdown,
  which would stop the new instance's Postgres by pid file and XPC services by executable name). It
  calls `terminate:` from the run loop, not from a main-actor task, where AppKit's wait for a
  `.terminateLater` reply deadlocks. The new instance waits for the old one to exit, then initializes a
  new cluster, applies the schema and re-syncs the sources from `garage.json` (`finishDatabaseReset`;
  the Database page shows `isFinishingDatabaseReset` as a progress line until the outcome arrives).
- Postgres is stopped with SIGINT (fast shutdown), never SIGTERM: a smart shutdown waits on the XPC
  services' pooled connections until the grace period ends in SIGKILL, leaving no shutdown checkpoint.
- `OperationRunner` runs app operations as gRPC calls (`GarageGRPCService+Operations.swift`) with a
  busy flag and rolling log; AppState keeps dedicated runners for `backfill`/`enrich-facts` so
  long-running jobs don't block ordinary operations. Ingest goes through `IngestService`, which
  drives `GarageIngestXPCService` via `IngestClient`. An ingest of every source takes sources from
  `AppState.ingestQueue`; `cancelAll()` empties the queue and stops the scan or ingest in progress,
  plus the backfill of a maintenance run and the facts step of Update Everything, and `cancel(source:)` / `removeSource(slug:)` act on one source even while
  it is busy. "Update Everything" on the Sources page (`AppState.updateEverything`) runs scan →
  ingest → embed → glean facts (`EnrichFacts` with `stale_only`) through the same `runPipeline` as
  scheduled maintenance, which stops after embed.
- `garage` and `garage-mcp` are Swift launchers (`Sources/GarageLauncher`) for people at a
  terminal and for stdio MCP clients: each sets the environment up and then calls the Rust CLI linked
  into it (`rust/garage-cli`'s `garage_cli_main` / `garage_mcp_main`), which runs GarageService in the
  launcher's own process. They are packaged as helper app bundles in `Contents/Helpers`
  (`garage.app` = `me.rickmark.garage-rag.garage-cli`, `garage-mcp.app` =
  `me.rickmark.garage-rag.mcp-server-cli`; `bazel/launcher_app.bzl`), each with its own
  entitlements and, in the signed distributions, provisioning profile so it can read the App Group
  keychain. The stable paths
  `Contents/MacOS/garage` and `garage-mcp` are symlinks (made by `link_launchers.sh`, the app's
  `ipa_post_processor`; codesign rejects a script in `MacOS` but seals a symlink) to `/bin/sh`
  forwarders in `Resources/launchers` that `exec` the helper by its real path (not Mach-O: a
  sandboxed forwarder could not start a helper with its own sandbox). When a command needs the
  database and nothing listens on its socket
  they open the app hidden (`--background`), then read the Postgres password from the Keychain
  and export `GARAGE_DATABASE_URL`, `GARAGE_SQL_DIR` (the bundled schema), `GARAGE_MODEL_MANIFEST`,
  `GARAGE_MCP_EXECUTABLE` and the app's sockets; stdio registrations therefore carry no database URL. Only
  these bundled launchers do this; a bare `garage` binary reads its config alone. `garage quit` (launcher only,
  never the CLI) posts a distributed notification that makes every running Garage quit as its Quit
  menu item does, and waits for it; use it before a UI test run, which refuses to share the Mac
  with a running Garage.
- MCP clients use stdio by default: the MCP page registers the bundled `garage-mcp` launcher
  (`McpInstall` with `stdio`), and each assistant spawns its own. `GarageMCPService` can also run a
  long-lived `garage-mcp` HTTP process at `127.0.0.1:8787/mcp`, the app's only TCP listener, but only
  once the user starts it (`garage.mcp.httpEnabled`; an upgrade with an HTTP registration keeps it
  on). While it is off, an HTTP registration shows as out of date and Update rewrites it to stdio.
- `LlamaXPCService` hosts llama.cpp itself (`macapp/Sources/LlamaEngine`, statically linked from
  `//ext/llama_cpp`, Metal + Accelerate) and serves it two ways: NSXPC for the app (load/unload,
  health, test calls, and `handleServerRequest`, which the other XPC services' embed-worker hosts call)
  and a llama-server-compatible HTTP API on its socket (`s/llama` in the group container,
  `GARAGE_LLAMA_SOCKET`; a loopback port only with `GARAGE_LLAMA_HTTP_PORT`) for processes outside
  them, the launchers' `llama_xpc` provider (`backfill`, `enrich-facts` run in their own process). Both front ends live
  in `macapp/Sources/LlamaServiceHost`, which takes any `LlamaInferenceEngine`; the other engines
  are test-only, in `macapp/Tests/LlamaTestSupport`: `MockLlamaServerEngine` for the unit tests,
  and `DeterministicLlamaEngine` (hashed bag-of-words embeddings, one grounded fact per sentence),
  which `macapp/Tests/MockLlamaXPCService` serves under LlamaXPCService's bundle identifier in
  `GarageApp_uitest`, the testonly host of the model UI tests (`macapp/Tests/GarageAppModelUITests`).
  Both apps come from `garage_macos_application` in `bazel/garage_app.bzl`.
  The app loads the default `llama_xpc` embedding model once Postgres is up (and again when the
  default changes), and loads the facts model only for a distillation run, unloading it afterwards
  unless it is also the search model (`AppState+LlamaModels.swift`). Other models load on demand and
  stay until the Models page's Unload. The on-demand loads run in garage-xpc, embed-xpc and
  mcp-server-xpc (through `LlamaModelLoader`), which cannot look up a sibling XPC service by name: the app's `LlamaEndpointBroker`
  (in `XPCServiceManager`) fetches the endpoint of LlamaXPCService's anonymous listener
  (`getListenerEndpoint`) and hands it to each (`setLlamaEndpoint`, `GarageLlamaEndpointStore`),
  again whenever either side's connection is lost; until then loads fail with "endpoint not handed over yet".
- Folder grants reach the sandboxed services as `URL`s over NSXPC, never as the app's bookmark bytes
  (app-scoped, so they resolve to no access in another process). `VolumeAccessService` hands each
  grant (root, per source, and an MCP config file picked in a panel) through `XPCFolderAccessRelay` to
  the ingest service and GarageXPCService (Scan, AddSource, McpInstall), whose
  `GarageFolderAccessStore` starts accessing it and keeps a bookmark of its own for relaunches.
- `GarageUpdater` wraps Sparkle (`//ext/sparkle`) for Developer ID builds; App Store builds
  `select()` in an inert backend instead, since Apple rejects self-updating apps, and Sparkle
  never enters that dependency graph. The appcast lives at `docs/appcast.xml` on the Jekyll
  site; the signing key and the release flow are garage-enterprise's (`docs/RELEASING.md` there).
- **Signed builds.** The App Store build and the Sparkle feed come from garage-enterprise (Rick,
  2026-11-01). A notarized Developer ID build for GitHub releases can also be made here (Rick,
  2026-11-04): `--config=developer_id` (`//bazel:developer_id`) and `//macapp/package`
  (`GarageApp`, `notarize_all`, `install`) sign with the keychain's Developer ID certificates and the
  installed Developer ID profiles, found by `bazel/signing_identity.bzl`; nothing team-specific is
  checked in (RELEASING.md, "GitHub release"). This repository keeps the seam they plug
  into, `bazel/platforms.bzl`: `signed_macos_platform` sets rules_apple's `signing_certificate_name`,
  `//bazel:distribution` (`developer_id` | `store`, behind `//bazel:is_developer_id` / `is_store`) and
  the three provisioning-profile label flags; `codesign` targets name no identity and take the flag's.
  Builds here sign with the best identity the keychain has (`//bazel:local_auto`, the default;
  `bazel/signing_identity.bzl`): an Apple Development certificate (Team ID, no profile, no hardened
  runtime; `//bazel:is_local_development`, and the App Group too when it is the group's team,
  `//bazel:is_local_app_group`), else the self-signed local identity, else ad hoc.
  `--config=adhoc` (CI) and `--config=local_signed` force one; `GARAGE_SIGNING_IDENTITY` in the environment
  (or `build --repo_env=` in `user.bazelrc`; `aspect` rejects it on the command line) names one.
- `FirstRunCoordinator` (+ `Views/FirstRunView.swift`) is the first-run setup assistant that replaces
  the sidebar UI until the user finishes or skips it (`garage.firstRun.completed` default): wait for
  services → pick template sources → pick embedding/distillation models → connect MCP clients. It
  goes through the same `AppState.addSource` / `registerModel` / `setFactsModel` operations and
  `GarageMCPService` registration as the Sources, Models and MCP pages.
- The sidebar (`AppSection` / `SidebarGroup` in `Views/ContentView.swift`) puts Status on top, then
  Configuration (Sources, Models, MCP Server), Data (Documents, Facts, Graph, Search) and Advanced
  (Database, Logs); `AppSection`'s cases follow that order, and a unit test holds them together.
  Page wording is kept in plain presentation values beside each view (`StatusPagePresentation`,
  `SourcesPresentation`, `DatabasePresentation`, `MCPServerPresentation`) with unit tests.
- Every helper runs its self tests at bootstrap, before it has any configuration, so the
  Database Connection and gRPC Connection tests of the ingest, embed and MCP helpers are skipped
  then. `AppState.startBackend` therefore pushes the database URL and the backend's address to
  them (`XPCServiceManager.configureHelpers`, over `updateConfiguration`) once the gRPC server
  listens and re-runs their tests; the backend helper gets the same keys from `startServer`. A
  test still skipped is named in the Status page's row ("7 passed, 1 skipped (Model File)").
- Each `*XPCService` (`GarageXPCService`, `GarageEmbedXPCService`, `GarageIngestXPCService`,
  `GarageMCPServerService`, `LlamaXPCService`, `ModelDownloadXPCService`, `GarageImageEmbedXPCService`)
  is a separate XPC service process paired with a `*Client` module (`IngestClient`, `EmbedClient`,
  `LlamaClient`, `ModelDownloadClient`, `ImageEmbedClient`, `MCPServerClient`) — this is the
  isolation boundary between the SwiftUI app and long-running/native work, distinct from the gRPC
  bridge to `GarageService`.
  - What every service shares is `GarageXPCKit`: `GarageXPCServiceBase`, self tests, logging, crash
    handling, the managed-service host, the peer requirement, and the types the app and the services
    pass each other (`GarageAppGroup`, `GarageSockets`, `GaragePostgresEndpoint`, the folder-access and
    endpoint stores, `GarageInProcessServices`). It links no framework of its own.
  - The Rust services (`GarageXPCService` on `garage-service-ffi`, `GarageIngestXPCService` on
    `garage-ingest-ffi`, `GarageEmbedXPCService` on `garage-embed-ffi`, `GarageMCPServerService` on
    `garage-mcp-ffi`) link their library statically, with `GarageEmbedWorkerHost` carrying the host
    calls (model servers over URLSession, `llama_xpc` and the image models over NSXPC).
    `LlamaModelLoader` and `ImageEmbedBridge` are the loaders those hosts share.
  - Every connection a listener accepts, from the service listener and the anonymous ones, carries
    `GarageXPCPeerRequirement` (set on the connection in `listener(_:shouldAcceptNewConnection:)`, never
    on the listener: on `NSXPCListener.service()` that crashes the service at launch): a peer must be
    Apple-signed with the service's own team. A process signed without a team (ad hoc, tests) checks nothing.
- The sandboxed (App Store) app hosts `GarageIngestXPCService`, `GarageXPCService` and
  `GarageEmbedXPCService` (whose image models read image files) in its own process
  (`InProcessServiceHost`), because only the app can read the folders the user granted: a URL
  sent over NSXPC arrives in a separately sandboxed service without its sandbox extension. Each
  service's delegate lives in a `*Core` library the app links, and the app registers an anonymous
  listener for it with `GarageInProcessServices`; every connection is made with
  `GarageInProcessServices.makeConnection(serviceName:)`, which reaches a registered service there
  and any other by name. `XPCServiceManager` never kills its own pid, so Restart leaves the app up.
  The Developer ID build is not sandboxed and runs every service out of process.

## Conventions worth knowing

- Rust: the toolchain in `rust/rust-toolchain.toml`, rustfmt (`rustfmt.toml`) and clippy at
  `-D warnings` with the workspace lints (`clippy::pedantic`). The Python development tools
  (`tools/`, `winapp/bazel`, `macapp/Tests/Fixtures/make_corpus.py`) run on the system's Python 3.13+
  and keep Ruff clean (`ruff.toml` at the root: `E,F,I,UP,B,SIM`, 120-col lines).
- After editing `proto/garage.proto` or `proto/garage_plugin.proto`, regenerate the checked-in Rust
  code: `cargo run -p protogen` (needs `protoc`); CI fails when it is stale. The Swift and C# stubs are
  built from the proto by Bazel and `dotnet build`.
- The model catalog is `data/models/models.json` (`//data/models`): the app bundles it and
  `garage-service`'s `catalog.rs` reads it. The site serves a copy at `https://garagerag.app/.data/models.json`,
  which the build puts in place (`site_files` on `//docs:site`, which `.github/workflows/pages.yaml`
  publishes); `docs/.data/models.json` is git-ignored, never edited.
- Keep licenses permissive: no AGPL or GPL dependency (`stage.ps1` refuses a DLL on its denylist,
  and the notices script lists every crate's license).
- Engineering plans live in `docs/plans/` and are published at `https://garagerag.app/plans/`; the index page
  (`docs/plans/index.md`) lists each one from its front matter (`title`, `description`, `date`, `status`,
  `status_kind`: `proposed` | `active` | `landed` | `deferred` | `reference`). A plan whose state has moved
  on opens with a status note; the text below it stays as written.
- `data/notices/THIRD_PARTY_NOTICES.txt` (shipped in the app's `Resources`) carries the license text
  of every redistributed component. It's generated by `python3 tools/third_party_notices.py` from
  `rust/Cargo.lock` (the crates reachable from the shipped crates, each license file from the
  published crate) plus `NATIVE_COMPONENTS` in that script — regenerate it after changing
  dependencies or anything under `ext/`; `//data/notices:third_party_notices_test` and CI's rust job
  enforce it.

## Project conventions

Decisions Rick made while building 1.5 that no file in the tree records. They hold until he says otherwise, and
are dated so a stale one can be spotted.

### Repositories and branches

- This repository is `lwm-luminx/garage-rag` (formerly `rickmark/garage-rag`; the old name redirects). It is
  the FOSS app. Non-FOSS and Enterprise work goes in `lwm-luminx/garage-enterprise`, which carries this
  repository as a submodule tracking `next` (Rick, 2026-10-05).
- New PRs target **`next`** (the next feature release). Only bugfixes target `main`, which is what releases and
  the site (garagerag.app, GitHub Pages) publish from. `main` flows into `next` through a merge PR merged with
  "Create a merge commit" (Rick, 2026-09-30). Both branches are protected by one ruleset, "Protected: main and
  next": PR required (merge or squash), signed commits, no force-push or deletion.
- Required checks (Rick, 2026-11-04): `aspect / buildifier`, `aspect / format`, `aspect / gazelle` and `aspect / lint`,
  the check runs the Aspect Workflows GitHub App posts for the `aspect` job's tasks (they take precedence over the
  job's own check), plus the Actions jobs "Swift:
  syntax check (tree-sitter)" and "Rust: fmt, clippy and tests (rust/)". The `aspect /` check appears only when CI
  signs in to Aspect (`ASPECT_API_TOKEN`), so a fork's PR needs an admin bypass. winapp-bazel and the macOS, Windows and known-answers jobs are not required;
  the notarized Developer ID build (made from garage-enterprise) is the release gate. Renaming a required job or
  task means updating the ruleset with it.
- A PR that contains merge commits cannot be rebase-merged on GitHub; it needs "Create a merge commit".
- Stacked PRs: when another branch or open PR already works on the same part of the app, base new work on it
  rather than on `main`/`next`, and name the base in the PR (Rick, 2026-09-24). When stacked PRs merge top-down
  after the lower one landed, check each merged PR's base still leads to the target branch.
- Open PRs early as drafts; mark one ready as soon as the work is complete and the checks that can run locally
  pass, without waiting for CI (Rick, 2026-09-25 and 2026-09-27).
- Follow-ups to a merged PR go on a new branch and PR, never a force-push of the merged branch.
- Branch deletion: list the branches and let Rick delete them himself.
- Review findings get labels unique across reviews, not S1..Sn reused per review (Rick, 2026-09-25).
- Every commit and tag is signed; the rulesets require verified signatures on `main`. Never force-push `main`.
  Commits sent upstream (rules_apple, PostgreSQL) never carry the Claude trailer.

### Product decisions

- Apple Silicon only; never add x86_64/universal builds, downloads or wording (2026-09-24).
- Minimize dyld runtime loading and binding: prefer static linking or load commands over `dlopen`/`ctypes`, and an
  in-process library over fork/exec of a tool. Dependencies were gathered into one framework to
  avoid duplication (2026-09-29); since the Python removal each Rust library links its own statically.
- IPC: XPC with code-signing checks; no new network listeners; serving remote clients is an opt-in for power
  users, never the default (2026-09-25).
- The bundled OpenSSL stays; no BoringSSL/LibreSSL swap (2026-09-25). One TLS stack for grpcio and cryptography
  is a later idea, not planned work.
- Distillation and inference share `inference_models` in `models.json`, tagged per use; the setup assistant asks
  only for the distillation model and chat follows it unless `inference.model` is set (2026-09-27).
- v2 (not 1.5.x): several Macs answering from one corpus over Garage's own peer protocol, Postgres hidden;
  several corpora on one Mac, chosen by `garage-mcp --corpus <name>` on stdio and a `/mcp/<name>` path on HTTP,
  never by a `corpus` argument on MCP tools.
- Cloud placeholders (v1.5.5, `next`): eviction is per source, one global disk cap for materialized files,
  provider APIs (Dropbox, OneDrive) opt-in and metadata only.
- Contact names come from Contacts and iMessage's shared names; test data is generated with Faker.
- The Sparkle appcast has a beta channel (`--channel beta`); through 1.5 every entry went to all installs ("until
  1.5 final, beta is also the main channel", 2026-09-28). Ask before publishing a beta-only entry.
- Alphas and betas ship as GitHub pre-releases from signed `v<ver>-alpha.N`/`-beta.N` tags. Tag only after the
  build from that commit is verified, and never move or patch a release tag: fixes go on a branch off it.
- The app prefers the site's `models.json` (served from `main`) over the one it bundles, so a catalog change that
  older builds would misread must reach the site with care, and a beta that changes the catalog needs the site's
  copy updated first.
